# Publish AUR package

[![CI](https://github.com/ulises-jeremias/github-actions-aur-publish/actions/workflows/ci.yml/badge.svg)](https://github.com/ulises-jeremias/github-actions-aur-publish/actions/workflows/ci.yml)
[![Release](https://img.shields.io/github/v/release/ulises-jeremias/github-actions-aur-publish)](https://github.com/ulises-jeremias/github-actions-aur-publish/releases)
[![Discord](https://img.shields.io/discord/1527933660764831825?label=Discord&logo=discord&logoColor=white)](https://discord.gg/bR5VyATgka)

GitHub Action to publish a package to the [Arch User Repository (AUR)](https://aur.archlinux.org/).

## Inputs

- `pkgname`

  **Required** AUR package name.

- `pkgbuild`

  **Required** (unless `asset_dir` is set) Path to the PKGBUILD file. This file is often generated by prior steps.

- `assets`

  **Optional** Newline-separated glob patterns for additional files to be added to the AUR repository.
  Glob patterns are expanded by bash when copying the files to the repository.
  Note that `assets` only ever *adds* or *overwrites* files; files removed from
  `assets` are **not** deleted from the AUR repository. Use `asset_dir` if you
  need removals to propagate.

- `asset_dir`

  **Optional** Path to a directory whose contents mirror the AUR repository.
  Unlike `assets`, `asset_dir` makes the AUR repository an exact mirror of the
  given directory: files tracked in the AUR repository but absent from
  `asset_dir` are **deleted**, so removals propagate. A `.gitignore` inside
  `asset_dir` is respected when deciding which files to copy.
  Because `asset_dir` is the full source of truth, it **must contain the
  `PKGBUILD`** and is **mutually exclusive** with both `pkgbuild` and `assets`.

- `commit_username`

  **Required** The username to use when creating the new commit.

- `commit_email`

  **Required** The email to use when creating the new commit.

- `ssh_private_key`

  **Required** Your private key with access to the AUR package.

- `commit_message`

  **Optional** Commit message to use when creating the new commit.
  The default value is `Update PKGBUILD and .SRCINFO with GitHub Actions`.

- `allow_empty_commits`

  **Optional** Allow empty commits, i.e. commits with no change. The default value is `true`.

- `force_push`

  **Optional** Use `--force` when pushing to the AUR. The default value is `false`.

- `ssh_keyscan_types`

  **Optional** Comma-separated list of key types to use when adding `aur.archlinux.org`
  to known hosts. The default value is `rsa,ecdsa,ed25519`.
  (`dsa` is filtered out automatically because modern OpenSSH rejects it.)

- `update_pkgver`

  **Optional** Run `makepkg -od` to update `pkgver`. Requires that the `pkgver()`
  function defined in the `PKGBUILD` file doesn't require any dependencies other than git.
  The default value is `false`.

- `updpkgsums`

  **Optional** Update checksums using `updpkgsums` before generating `.SRCINFO`.
  The default value is `false`.

- `test`

  **Optional** Check that the PKGBUILD can be built before publishing.
  The default value is `false`.

- `test_flags`

  **Optional** Command line flags for `makepkg` when `test` is enabled.
  The default flags are `--clean --cleanbuild --nodeps`.

- `post_process`

  **Optional** Commands to execute after processing the package, before
  committing — an escape hatch for tweaks the action doesn't cover
  (e.g. appending a footer to the generated files). Runs with `eval` inside
  the prepared repository, so only use commands you trust.

- `dry_run`

  **Optional** Validate and prepare everything, then show what would be
  published without committing or pushing. Useful to trial workflow changes
  safely. The default value is `false`.

- `aur_branch`

  **Optional** Branch to push to on the AUR remote. The default value is `master`
  (the branch the AUR uses).

- `push_retries`

  **Optional** How many times to retry `git push` (the AUR goes down for maintenance
  regularly). The default value is `12`.

- `push_retry_seconds`

  **Optional** Seconds to wait between push retries. The default value is `20`.

## Outputs

- `commit_sha` — SHA of the commit published to the AUR.
- `package_url` — URL of the AUR package page
  (`https://aur.archlinux.org/packages/<pkgname>`).
- `package_version` — `pkgver` of the published package.

```yaml
- name: Publish AUR package
  id: aur
  uses: ulises-jeremias/github-actions-aur-publish@v1
  with:
    pkgname: my-awesome-package
    # ...
- name: Show result
  run: |
    echo "Published ${{ steps.aur.outputs.commit_sha }}"
    echo "${{ steps.aur.outputs.package_url }}"
```

## Example usage

```yaml
name: aur-publish

on:
  push:
    tags:
      - "*"

jobs:
  aur-publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4

      - name: Publish AUR package
        uses: ulises-jeremias/github-actions-aur-publish@v1
        with:
          pkgname: my-awesome-package
          pkgbuild: ./PKGBUILD
          commit_username: ${{ secrets.AUR_USERNAME }}
          commit_email: ${{ secrets.AUR_EMAIL }}
          ssh_private_key: ${{ secrets.AUR_SSH_PRIVATE_KEY }}
          commit_message: Update AUR package
          ssh_keyscan_types: rsa,ecdsa,ed25519
          update_pkgver: false
```

**Note:** Replace `v1` with an exact tag (e.g. `v1.2.3`, immutable) if you prefer
to only pick up changes you have explicitly reviewed. See [Releases](#releases).

**Tip:** To create secrets (such as `secrets.AUR_USERNAME`, `secrets.AUR_EMAIL`,
and `secrets.AUR_SSH_PRIVATE_KEY` above), go to
`$YOUR_GITHUB_REPO_URL/settings/secrets`.
[Read this for more information](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions).

**Tip:** This action does not generate a PKGBUILD for you, you must generate it
yourself (e.g. with steps before this action).

**Tip:** Upload the *public* key matching `ssh_private_key` to your
[AUR account](https://aur.archlinux.org/account/) under "My Account → SSH Public
Key", otherwise the push fails with `Permission denied (publickey)`.

### Publishing extra files with `assets`

```yaml
- name: Publish AUR package with install script
  uses: ulises-jeremias/github-actions-aur-publish@v1
  with:
    pkgname: my-awesome-package
    pkgbuild: ./PKGBUILD
    assets: |
      ./my-awesome-package.install
      ./patches/*.patch
    commit_username: ${{ secrets.AUR_USERNAME }}
    commit_email: ${{ secrets.AUR_EMAIL }}
    ssh_private_key: ${{ secrets.AUR_SSH_PRIVATE_KEY }}
```

### Publishing multiple packages (matrix)

```yaml
jobs:
  aur-publish:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    strategy:
      matrix:
        package: [my-awesome-app, my-awesome-app-bin]
    steps:
      - uses: actions/checkout@v4

      - name: Publish ${{ matrix.package }}
        uses: ulises-jeremias/github-actions-aur-publish@v1
        with:
          pkgname: ${{ matrix.package }}
          pkgbuild: aur-package/${{ matrix.package }}/PKGBUILD
          commit_username: ${{ secrets.AUR_USERNAME }}
          commit_email: ${{ secrets.AUR_EMAIL }}
          ssh_private_key: ${{ secrets.AUR_SSH_PRIVATE_KEY }}
          commit_message: Update AUR package
          allow_empty_commits: false
```

### Permissions

This action only needs read access to your repository (to check out the
PKGBUILD) plus network access to the AUR. Follow the principle of least
privilege and declare restrictive permissions on the calling job:

```yaml
permissions:
  contents: read
```

The default `GITHUB_TOKEN` permissions of your repository apply otherwise;
avoid granting `contents: write` when the workflow only publishes to the AUR.

## Troubleshooting

### `Permission denied (publickey)`

The SSH key was rejected by the AUR. Check that:

1. The *public* key matching `ssh_private_key` is uploaded to your AUR account
   ("My Account → SSH Public Key").
2. The secret contains the full private key, including the
   `-----BEGIN ... PRIVATE KEY-----` / `-----END ... PRIVATE KEY-----` lines.
3. The key has access to the package — for a new package, the first push must
   come from the maintainer account that will own it.

### `makepkg` fails (missing dependencies)

`.SRCINFO` is generated with `makepkg --printsrcinfo`, which needs the
`sources` of the PKGBUILD to be resolvable. If your `pkgver()` or the
`PKGBUILD` itself needs extra tools, install them in a prior step that
generates the PKGBUILD, and keep this action's input as the final file.
With `update_pkgver: true`, `pkgver()` must only depend on `git`.

### `Destination path '/tmp/local-repo' already exists`

This comes from the clone step and should not happen in a fresh container. If
you see it, you are likely running the action's scripts outside Docker (e.g.
in local tests reusing `/tmp/local-repo`) — remove that directory and retry.

### Push fails during AUR maintenance

The AUR is regularly unavailable during maintenance windows. The action retries
the push (`push_retries`, default `12`, waiting `push_retry_seconds`, default
`20`s, between attempts) and only fails after exhausting them. If publishing
is urgent, re-run the workflow later; otherwise increase `push_retries`.

### Invalid PKGBUILD error (exit code 4)

Before publishing, the action checks the PKGBUILD with `bash -n` and verifies
it declares `pkgname`, `pkgver`, `pkgrel`, `arch`, and `license`. A failure
lists the missing field — fix the generating step and re-run.

## Releases

This project follows [Semantic Versioning](https://semver.org/). Two kinds of
tags exist, and they're pinned differently:

- **Exact tags** (`v1.2.3`) are immutable once published - the same tag
  never points to different code. Pin to one of these if you want your
  workflow to only ever pick up a change you've explicitly reviewed.
- **Major tag** (`v1`) is a rolling tag that we move forward to the latest
  compatible release. This is what the [example usage](#example-usage)
  above and most consumers pin to - the standard convention for GitHub
  Marketplace actions (the same one `actions/checkout` or
  `actions/setup-node` use), so a `v1` pin keeps receiving non-breaking
  fixes automatically without you having to bump anything.

Release notes are drafted automatically as pull requests are merged, via
[Release Drafter](https://github.com/release-drafter/release-drafter)
(configured in
[`.github/release-drafter.yml`](./.github/release-drafter.yml) and
[`.github/workflows/release-drafter.yml`](./.github/workflows/release-drafter.yml)).
The categorized draft becomes that release's notes when it's published, and
its summary is copied into [`CHANGELOG.md`](./CHANGELOG.md).
